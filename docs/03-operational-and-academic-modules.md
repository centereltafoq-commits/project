# التوثيق التشغيلي للوحدات الأكاديمية والإدارية (Academic & Operational Modules)
> **EduCenter ERP** — نظام إدارة السنتر التعليمي المتكامل  
> **الإصدار البرمجي:** 1.0.0 | **تاريخ التوثيق:** نوفمبر 2026

## 1. إدارة شؤون الطلاب (Students Management)

### 1.1. دورة حياة الطالب وحالات القيد (`StudentStatus`)
يمر الطالب في النظام بثلاث حالات أساسية:
- **`ACTIVE` (نشط):** الطالب مقيد ومنتظم في المجموعات الدراسية، يظهر في كشوف الحضور والغياب، ويتم احتساب اشتراكاته في التسويات الشهرية.
- **`SUSPENDED` (موقوف مؤقتاً):** إيقاف مؤقت لأسباب انقطاع أو سفر؛ يحتفظ بسجلاته ولا يُحاسب عن الشهور التي لا يوجد له فيها اشتراك مفعل.
- **`ARCHIVED` (مؤرشف):** انتهاء الدراسة أو تخرج الطالب مع الاحتفاظ الكامل بتاريخه الأكاديمي والمالي لسنوات سابقة.

### 1.2. المعايير الصارمة لبيانات الطالب
1. **كود الطالب الفريد (`student_code`):** يُنشأ تلقائياً بنمط تسلسلي آمن (مثل `STU-1001`) لمنع التكرار نهائياً.
2. **التحقق من أرقام الهواتف:** يلزم إدخال رقم هاتف الطالب ورقم هاتف ولي الأمر بصيغة صحيحة (تتطابق مع معايير شبكات المحمول المصرية 11 رقماً).
3. **البحث السريع والفهرسة:** يدعم جدول الطلاب فهارس ثلاثية المقاطع (`pg_trgm`) على الاسم الكامل، مما يتيح البحث الفوري حتى مع الأخطاء الإملائية الشائعة أو البحث بجزء من الاسم أو برقم الهاتف.
4. **ملف الطالب المالي والأكاديمي المتكامل (`Student Profile`):** يوفر بروفايل الطالب ملخصاً شاملاً يضم:
   - الاشتراكات الحالية والسابقة في كافة المجموعات.
   - كشف حساب مالي تفصيلي شهري (المستحق، المدفوع، المتبقي لكل مجموعة).
   - سجل حضور وغياب تفصيلي بنسب مئوية دقيقة وإحصائيات الحصص التعويضية.
   - سجل الإيصالات والمقبوضات الصادرة باسم الطالب.

## 2. إدارة المدرسين والمساعدين (Teachers & Assistants)

### 2.1. إدارة المدرسين (`Teachers`)
- **البيانات التعاقدية والتخصص:** تسجيل الاسم، رقم الهاتف، التخصص التدريسي (مثل "كيمياء ثانوية عامة")، وتاريخ التعاقد.
- **الحالة الوظيفية (`TeacherEmploymentStatus`):** `ACTIVE` (على رأس العمل)، `ON_LEAVE` (إجازة مؤقتة)، `INACTIVE` (منهي التعاقد).
- **الربط بحسابات النظام (`user_id`):** يمكن ربط بروفايل المدرس بحساب مستخدم من خلال لوحة التحكم؛ يمنح هذا الربط المدرس إمكانية تسجيل الدخول عبر البوابة بصلاحيات خاصة (`teachers.view_own`):
  - عرض مجموعاته وحصصه فقط دون الاطلاع على باقي السنتر.
  - رصد حضور وغياب طلاب مجموعاته.
  - استعراض طلبات الحجوزات الخاصة به واعتمادها أو تعديلها (`bookings.approve_teacher`).
- **محاسبة المدرسين:** احتساب مستحقات المدرسين وفق السياسة المعتمدة لكل مجموعة، وإصدار أذونات الصرف النقدية (`teacher_payouts`) برقم مرجعي مميز (`TPY-...`).

### 2.2. إدارة المساعدين (`Assistants`)
- **تنوع طرق احتساب الأتعاب:** يدعم النظام 7 نماذج محاسبية لأتعاب المساعدين تبدأ من العمولة على إيراد الحصص، أو أجر الحصة الواحدة، أو أجر الساعة، وصولاً للمرتب الشهري المقطوع أو الاتفاق المخصص.
- **تخصيص الأتعاب للمجموعات (`Group Override`):** يتيح السنتر تخصيص طريقة حساب أو قيمة مختلفة للمساعد عند عمله مع مجموعة معينة دون تغيير بروفايله العام؛ في هذه الحالة يطبق النظام قاعدة الأسبقية:
  $$\text{Effective Rate} = \text{Override Rate (إن وُجد)} \parallel \text{Base Assistant Rate}$$

## 3. المجموعات الدراسية والاشتراكات (Groups & Enrollments)

### 3.1. خصائص المجموعة الدراسية (`groups`)
- **كود المجموعة واسمها:** كود فريد (مثل `GRP-MATH-202`)، واسم تعريفي واضح.
- **المدرس الأساسي والقاعة الافتراضية:** ربط المجموعة بالمدرس المسؤول وقاعتها المعتادة لتسريع جدولة الحصص تلقائياً.
- **تسعير المجموعة وحصصها:**
  - `monthly_sessions_count`: عدد الحصص الشهرية المستهدفة (مثلاً 8 حصص شهرياً).
  - `monthly_price`: سعر الاشتراك الشهري المعتمد.
  - `calculated_session_price`: سعر الحصة الفردي المحسوب ($\text{monthly\_price} / \text{monthly\_sessions\_count}$).
- **جدول المواعيد الأسبوعي (`schedule_slots`):**
  مصفوفة JSON تُحدد أيام وساعات انعقاد المجموعة أسبوعياً:
  ```json
  [
    { "dayOfWeek": 0, "startTime": "16:00", "endTime": "18:00", "classroomId": "uuid-1" },
    { "dayOfWeek": 3, "startTime": "16:00", "endTime": "18:00", "classroomId": "uuid-1" }
  ]
  ```
- **السعة القصوى (`max_students`):** تحديد حد أقصى للطلاب لمنع تكدس القاعات ومطابقة مقاعد القاعة.

### 3.2. توليد حصص الشهر آلياً (`buildMonthSessionDates`)
بضغطة زر واحدة في بداية الشهر المالي، يقوم النظام بقراءة `schedule_slots` وتوليد كافة حصص الشهر تلقائياً مع حساب أيام التقويم الفعلي:
```typescript
for (let day = 1; day <= daysInMonth; day++) {
  const utcDate = new Date(Date.UTC(year, monthIndex, day));
  const dayOfWeek = utcDate.getUTCDay();
  for (const slot of slots) {
    if (slot.dayOfWeek === dayOfWeek) {
      // توليد حصة مؤكدة في تاريخ اليوم مع أوقات البداية والنهاية والقاعة
    }
  }
}
```

### 3.3. اشتراكات الطلاب المرنة (`enrollments`)
يدعم النظام اشتراكات الطلاب المخصصة دون التقيد بنموذج ثابت:
- تحديد تاريخ بدء اشتراك الطالب (`start_date`) مع دعم بدء الاشتراك بمنتصف الشهر.
- إمكانية تحديد سعر شهري مخصص للطالب (`agreed_monthly_price`) وسعر حصة استثنائي (`agreed_session_price`) لدعم حالات المنح أو الأشقاء.
- إيقاف الاشتراك أو تجميده (`PAUSED` أو `COMPLETED`) مع تحديد تاريخ الانتهاء (`end_date`) للحفاظ التام على السجلات التاريخية للشهر.

## 4. الحصص والحضور والغياب والتعويضات (Attendance Engine)

### 4.1. حالات الحضور الأربعة (`AttendanceStatus`)
1. **`PRESENT` (حاضر):** الطالب حضر الحصة في موعدها وقاعتها.
2. **`ABSENT` (غائب):** غياب بدون إذن مسبق؛ يُسجل في إحصائيات الغياب ولا يُخصم من رسوم الطالب إلا وفق سياسة غياب الشهر كاملاً للمجموعة.
3. **`EXCUSED` (غائب بعذر):** غياب بإذن معتمد؛ يتم إعفاؤه مالياً ما لم تنص سياسة المجموعة صراحة على محاسبة الغياب بعذر (`chargeExcusedAbsence = true`).
4. **`MAKEUP_ATTENDED` (حاضر تعويض):** حضور الطالب في مجموعة أو موعد بديل لتعويض حصة سابقة غاب عنها؛ يُحسب له كحضور فعلي.

### 4.2. قواعد رصد الحضور الصارمة
- **منع التكرار:** قيد فريد في قاعدة البيانات `UNIQUE(session_id, student_id)` يمنع رصد الطالب مرتين لنفس الحصة.
- **التدقيق المزدوج:** يسجل النظام معرف الموظف الذي قام بالرصد الأولي (`recorded_by_user_id`) ومعرف الموظف الذي أجرى أي تعديل لاحق (`updated_by_user_id`) مع توقيت التعديل الدقيق.
- **التحقق من قيد الطالب:** لا يمكن رصد حضور طالب في حصة إلا إذا كان اشتراكه في المجموعة سارياً في تاريخ انعقاد تلك الحصة.

### 4.3. نظام حصص التعويض (`makeup_sessions`)
- عند تسجيل الطالب غائباً بعذر، يُتاح للإدارة فتح طلب حصة تعويضية مرتبطة بالحصة الأصلية (`original_session_id`).
- تحديد موعد التعويض والقاعة وحالة التنفيذ (`PENDING` -> `SCHEDULED` -> `COMPLETED` أو `CANCELLED`).
- إمكانية تحديد رسوم تعويض إضافية إذا نصت لائحة السنتر على ذلك (`isFree = false` و `extraFee > 0`)؛ تضاف هذه الرسوم آلياً إلى فاتورة الطالب الشهرية في محرك الفواتير.

## 5. محرك منع تعارض الحجوزات والقاعات (`Schedule Conflict Engine`)

يمثل محرك منع التعارضات (`ScheduleConflictChecker`) أحد أقوى ركائز الأمان التشغيلي في النظام؛ حيث يقوم بفحص لحظي متعدد الأبعاد قبل اعتماد أي حجز قاعة أو موعد درس خاص.

### 5.1. القواعد الخمس الصارمة لمنع التعارض

```
                      [فحص طلب الحجز]
                            │
      ┌─────────────────────┼─────────────────────┐
      ▼                     ▼                     ▼
[قاعدة 1: تعارض المدرس]  [قاعدة 2: تعارض الطالب]  [قاعدة 3: صيانة القاعة]
- لا تداخل مع حجز مؤكد   - لا تداخل مع حجز مؤكد   - القاعة ليست MAINTENANCE
- لا تداخل مع حصة مجموعة - لا تداخل مع حصة مجموعة - لا تداخل مع فترات الصيانة
      │                     │                     │
      └─────────────────────┼─────────────────────┘
                            │
      ┌─────────────────────┴─────────────────────┐
      ▼                                           ▼
[قاعدة 4: إشغال القاعة]                    [قاعدة 5: سعة القاعة]
- لا تداخل مع حجز قاعة إداري               - عدد الحضور المتوقع <=
- لا تداخل مع حصة مجموعة بالقاعة             السعة القصوى (maxCapacity)
                            │
                            ▼
              [إجازة الحجز أو رفضه بـ ConflictException]
```

### 5.2. التفصيل البرمجي لقواعد التعارض:
1. **`TEACHER_CONFLICT` (تعارض جدول المدرس):**
   - التحقق من عدم وجود حجز مؤكد آخر للمدرس في نفس اليوم يتداخل زمنياً:
     $$\text{Overlapping} = (\text{reqStart} < \text{existEnd}) \land (\text{reqEnd} > \text{existStart})$$
   - التحقق من عدم وجود حصة مجدولة لمجموعات المدرس في نفس التوقيت.
2. **`STUDENT_CONFLICT` (تعارض جدول الطالب):**
   - التحقق من عدم وجود حجز فردي مؤكد للطالب في نفس التوقيت.
   - التحقق من عدم وجود حصة لأي مجموعة مقيد بها الطالب تتداخل مع الموعد المطلوب.
3. **`CLASSROOM_UNAVAILABLE` (عدم جاهزية القاعة):**
   - التحقق من أن حالة القاعة هي `AVAILABLE` وليست `MAINTENANCE` أو `INACTIVE`.
   - فحص جدول صيانة القاعات (`classroom_maintenances`) للتأكد من عدم وجود صيانة دورية أو طارئة في ذلك النطاق الزمني.
4. **`CLASSROOM_OCCUPIED` (إشغال القاعة):**
   - التحقق من عدم تخصيص القاعة لحجز إداري آخر (`classroom_bookings`).
   - التحقق من عدم انعقاد حصة دراسية لمجموعة أخرى في نفس القاعة.
5. **`CLASSROOM_CAPACITY_EXCEEDED` (تجاوز السعة الاستيعابية):**
   - التحقق الصارم من أن عدد الحضور المتوقع للطلب (`expected_attendees`) لا يتجاوز الحد الأقصى لسعة القاعة (`max_capacity`).

## 6. دورة طلبات الحجز والاعتماد (`Booking Workflow`)

### 6.1. أنواع الحجوزات (`BookingRequestType`)
- **`STUDENT_WITH_TEACHER` (طالب مع مدرس):** حجز حصة فردية أو خاصة بين طالب ومدرس، تتطلب اعتماد المدرس أو إدارة السنتر وتخصيص قاعة مناسبة.
- **`TEACHER_WITH_CENTER` (مدرس مع سنتر):** حجز قاعة من قِبل مدرس لعقد محاضرة إضافية، مراجعة عامة، أو ورشة عمل.

### 6.2. مراحل دورة الحجز
1. **التقديم (`PENDING`):** يتم إنشاء الطلب مع تحديد الموعد، الغرض، وعدد الحضور، مع فحص أولي لعدم التعارض.
2. **المراجعة والاعتماد:**
   - يملك مدير السنتر صلاحية `bookings.approve_admin` لاعتماد أي حجز وتعيين القاعة النهائية.
   - يملك المدرس صلاحية `bookings.approve_teacher` لاعتماد الحجوزات المقدمة له مباشرة.
3. **التأكيد (`CONFIRMED`):** عند الموافقة، يتم تخصيص القاعة رسمياً في جدول `classroom_bookings` لمنع أي استخدام متزامن لها.
4. **التعديل أو الرفض (`MODIFIED` / `REJECTED`):** يمكن للمعتمد تعديل القاعة أو الموعد مع تدوين سبب التعديل أو الرفض في جدول `booking_approvals`.
5. **الإلغاء أو الإتمام (`CANCELLED` / `COMPLETED`):** إنهاء الحجز بعد تنفيذه أو إلغائه مع إخلاء القاعة فوراً للمواعيد الأخرى.
